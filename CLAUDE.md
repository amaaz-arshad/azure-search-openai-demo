## Contracts To Preserve

- Frontend chatbot routing is `/<chatbot_name>` inside each bot's `LayoutWrapper`; `/<chatbot_name>/*` renders that bot's `NoPage` outside the layout so fallback pages do not show chatbot chrome.
- All routes in `app/frontend/src/index.tsx` are nested under a single pathless layout route (`element: <Outlet/>`) whose `errorElement` is the self-contained `shared/error/RouteErrorBoundary.tsx`. This catches any render/commit error from ANY route (built-in bots, the `/:botName` generic bot, `/admin`, embed) and shows a friendly Reload fallback instead of React Router's raw developer error page — so one stray error (e.g. a browser extension tampering with the page) never white-screens the whole SPA. Do not remove this wrapper or add routes outside it. The boundary renders in place of the matched route (so the per-route `I18nextProvider`/`ChatbotThemeRoot` are NOT in scope): keep it provider-free — no `useTranslation`, no theme tokens, inline styles only, locale from `document.documentElement.lang`/`navigator.language`.
- `useEffect`/`useLayoutEffect` callbacks must never implicitly return a DOM API result — always use a block body (`useEffect(() => { el.scrollIntoView(...); }, deps)`, NOT `useEffect(() => el.scrollIntoView(...), deps)`). Browser smooth-scroll extensions patch `Element.prototype.scrollIntoView` to return an object; React stores a non-function return value as the effect cleanup and crashes calling it on the next effect re-run (`TypeError: m is not a function` in production — this took down every dynamic-bot session with browser history enabled). All 20 `pages/chat/Chat.tsx` scroll effects are block-bodied with a comment; don't "simplify" them back.
- Bots with frontend basic auth must guard both `LayoutWrapper` and standalone `NoPage`; otherwise `/<chatbot_name>/*` can bypass the gate.
- Chatbot basic auth for `agindo`, `demo`, `fbn`, `fhg`, `internal`, `knoll`, `moodle`, `rak`, `sartorius`, `steuertipps`, and `vjoonk4` uses server-side `/chatbot-auth/<chatbot_name>/*` HttpOnly cookies. `/chat` and `/chat/stream` intentionally remain ungated by that simple-auth cookie for iframe compatibility.
- Frontend login wrappers are API clients only. Do not reintroduce hardcoded browser-side credential checks.
- Backend `/config` is the frontend capability contract for model selection and reasoning effort. When model behavior changes, update backend metadata rather than hardcoding frontend assumptions.
- `/internal` is a router shell, not its own retrieval category. Internal requests must carry `context.overrides.source_chatbot`; backend validation derives the effective bot identity, prompt, and `include_category` from that selected source bot.
- `/config` includes `internalSourceBots` for the `/internal` source-bot dropdown. Do not reintroduce `All`; only one real source bot can be active per internal session.
- Internal chat history sessions must persist `source_chatbot` metadata. Legacy internal sessions without that metadata are intentionally hidden and non-restorable.
- Internal citations resolve against the selected source bot's content path while visible `/internal` branding stays fixed as `Internal Bot`.
- Backend startup auto-discovers optional chatbot backend modules under `app/backend/approaches/chatbots/<chatbot_name>/`. Do not add manual registration unless the code path truly requires it.
- The internal admin tools are consolidated under a single password-gated `/admin` shell (`app/frontend/src/pages/admin/AdminLayout.tsx`) with tabs: `/admin/chatbots` (directory — built-in **and** provisioned bots), `/admin/prompts`, `/admin/uploads`, `/admin/users` (nerilio users), and `/admin/embed` (iframes the backend-served `/embed-demo`). One login form (the shared `useInternalAdminAccess` cookie session, provided to tabs via `AdminShellContext`) gates every tab; the legacy paths `/chatbots`, `/manage-prompts`, `/upload-files`, `/free-users`, `/public-test-users` redirect client-side (React Router `<Navigate>`) into the matching tab, and the backend still serves the SPA for them so hard loads work. `admin` is a reserved prefix in `NON_CHATBOT_FRONTEND_PREFIXES` (so the `/<chatbot_name>` catch-all and dynamic-bot provisioning can't take it) and `app.py` serves the SPA for `/admin` + `/admin/<subpath>`. Auth is unchanged server-side: the `@internal_admin_required` data APIs (`/internal-admin/*`, `/managed_uploads`, `/free-admin/*`, `/public-test-admin/*`) still enforce the cookie, and `/chat`+`/chat/stream` stay ungated. Tab pages keep their own `.page` body; the shell owns the login gate, tab bar, "Lock admin" logout, and a `useBlocker`-based nav/logout guard that the Prompts (unsaved edits) and Uploads (active queue) tabs register into. - **Free Bot access is a 30-day trial, and an expired account is blocked but never deleted.** `FREE_ACCOUNT_LIFETIME_DAYS = 30` in `app/backend/core/freeauth.py` owns the whole rule; the frontend never computes an expiry date. Effective expiry = the account blob's stored `expires_at`, else `created_at + 30 days` — so the window applied **retroactively** on rollout (accounts registered more than 30 days before deploy were expired immediately, by explicit decision) and every account rewrite (`reset_account_password`, `verify_password_reset`) MUST carry `expires_at` through or an admin reactivation is silently undone. `expires_at` is written explicitly on signup and by `reactivate_account`; it is NOT in `load_account`'s required-field set (legacy blobs lack it). Unparseable timestamps count as expired (the record surfaces in the archive, where reactivating heals it). Blocking is enforced at four points: `load_session` returns None for an expired account — the single choke point for every authenticated request (chat, uploads, history), so access dies on the next request rather than at 7-day cookie expiry; `login_user` raises `authErrors.accountExpired` (403) but **only after** the password check, so it is not an oracle for which emails are registered; the password-reset trio raises the same; and signup (`start_signup`/`resend_signup_code`/`verify_signup`, via `raise_for_existing_signup_account`) raises the distinct `authErrors.accountExpiredSignup` — the expired blob is kept precisely so its email cannot be recycled into a fresh window, and "account already exists" would read as a mistake. Recovery is admin-only: `POST /free-admin/users/<email>/reactivate` (`reactivate_account`) sets `expires_at = now + 30 days`, keeping `created_at`, the password hash, and the user's uploads (expiry deletes NOTHING — uploads/indexed docs go only through the existing delete flow). `describe_account_expiry` is the one expiry formatter (`expiresAt`/`isExpired`/`daysRemaining`/`daysExpired`; `days_remaining` rounds **up** so a partial final day reads as 1, `days_expired` rounds down); it feeds `/free-admin/users`, `/free-auth/profile`, and — via `FreeSession.expires_at`/`days_remaining` and `build_free_session_payload` — every session response, so the bot shows the countdown with no extra request. The `/admin/users` tab splits that one list into **Active / Archive** tabs (expired accounts are listed, not hidden) with a per-card countdown, and only archive cards offer "Reactivate +30 days"; the Free Bot shows "Access until … (N days left)" in its profile modal plus a dismissible banner under the navbar inside `FREE_EXPIRY_WARNING_DAYS = 7` (defined in `pages/basicauth/basicAuth.ts`, mirrored by the admin card's warning highlight). That banner needs the layout to give it room: the free bot's chat sizes itself `calc(100vh - 56px - var(--free-expiry-notice-height, 0px))`, and `Layout.tsx` measures the rendered banner (ResizeObserver, so wrapping on narrow screens counts) into that variable on the layout root — with `.header { flex: none }` so the sticky 56px navbar is never flex-shrunk. Without the variable term the document overflows by the banner's height and the chat's auto-scroll immediately drags the banner up behind the opaque sticky navbar (verified: it was invisible before the fix). Anything else added between navbar and chat must feed the same variable. New backend-authored copy needs `authErrors.accountExpired`/`accountExpiredSignup`, `profile.expiresAt`/`daysLeft_one`/`daysLeft_other`, and `expiryNotice.*` in all three Free Bot locales (de/en/nl).

- Tutor-mode bots (`bensberg`, `demo`, `fbn`, `knoll`, `lemon`, `moodle`, `steuertipps`, and `internal` via its selected source bot) share a hardened tutor flow in each `sampleprompt.py`. A 🟠 P1 **Tutor Start Gate** forbids asking Frage 1 until topic **and** knowledge level (1–5) **and** number of questions (3/5/10) are all collected; the count question is mandatory (level vs. count is disambiguated because 3/5 overlap). Every tutor question is headed with a visible running counter rendered in the active `{{language_locale}}` — `Frage {{N}} von {{Total}}:` (de) / `Question {{N}} of {{Total}}:` (en) / `Vraag {{N}} van {{Total}}:` (nl); the word "Frage" is NOT a fixed literal, so each prompt's three governing counter rules (bold-allowance, the DETERMINISTIC QUESTION COUNT master bullet, the "Always head the question…" bullet) must list all three forms or the model emits German even in en/nl sessions. There is an absolute terminal stop: after the answer to the final question (`Frage {{Total}} von {{Total}}`), go straight to the Performance Summary — never ask beyond `{{Total}}`. A 🟠 P1 **Question Difficulty MUST Match Knowledge Level** section ties the chosen level `{{Level}}` to the *cognitive demand* of every question (Bloom-style: L1 recall → L3 apply → L5 evaluate/synthesize), with a per-question self-check ("could a user one level lower answer this just as easily?") and a hard ban on bare definition/recall questions at Level 4–5 — without this the model collapses every level to easy recall, so a Level-5 test feels like Level 1. `{{Level}}`/`{{Total}}`/`{{N}}`/`{{Topic}}` are model-filled narrative placeholders (only `SUPPORT_EMAIL`, `POSSIBLE_CITATIONS_PROMPT`, and `language_locale` are code-substituted in `render_chatbot_prompt`). These bots run `gpt-5.4-mini` at `reasoning_effort="high"` (set per bot in `config.py`; `registry.ts` `reasoningEffort` metadata mirrors it). Keep the gate, the visible counter, the level-difficulty rubric, and the high effort in sync across all tutor prompt variants (lemon/bensberg/internal, demo/fbn/moodle/steuertipps, and the compact knoll). (`publishone` was converted to a Q&A-only, English-only bot on 2026-07-23 — it no longer uses the tutor flow, option markers, or a wordmark answer logo; its prompt is a clean Q&A prompt in `sampleprompt.py`, model `gpt-4.1`, and its assistant avatar is `publishone_logo.jpeg` rendered snap-style outside-left.)
- Tutor-mode closed-choice prompts (mode, topic, knowledge level, question count, in-flow yes/no) render as interactive buttons via a hidden marker the model appends at the END of a message: `[[CHOICES kind=mode|topic|level|count|generic allowOther=0|1]]Label | Label[[/CHOICES]]`. It is parsed/stripped by `app/frontend/src/chatbots/shared/answer/optionMarkers.ts` and rendered by shared `AnswerOptions.tsx` inside `ChatbotAnswer` (same hidden-marker pattern as HYROX `assessmentMarkers.ts`). The marker stays in stored content (replays into history) but is display-stripped. `mode`/`level`/`count` carry an EMPTY body — the frontend supplies localized labels (and level descriptions) from each bot's `options.*` i18n keys (de/en/nl); `topic`/`generic` carry pipe-separated labels in the body. `level` and `count` are fixed sets and NEVER render an "Andere Option" — `parseChoiceMarker` force-disables `allowOther` for them regardless of what the model emits. Clicking sends the value as a normal request, but the user bubble is suppressed (`isOptionSelectionTurn`) and the choice is shown locked inside the assistant's option group (derived from `answers[i+1][0]`, survives history restore); "Andere Option" focuses the chat input for a free-typed answer (which still shows a normal user bubble); on send, that free-typed value is recorded in `pendingOptionSelection` so the "Other" highlight survives the `answers`↔`streamedAnswers` render switch (which remounts `AnswerOptions` and would otherwise drop its local optimistic-selected state until the response arrives). The welcome mode choice is the marker appended in each tutor `Chat.tsx` to `initialAssistantMessageContent` (the synthetic welcome pair is stripped before any backend call). A separate hidden bubble-split marker `[[SPLIT]]` (parsed by `splitBubbleSegments`, display-stripped) renders everything after it as a NEW assistant bubble inside the SAME stored message. The turn that evaluates the user's **answer** to the FINAL question (never the turn that asks it — asking `Frage {{Total}}` still stops and waits) emits the ending in ONE turn (no extra user input): the final-answer feedback, then `[[SPLIT]]`, the Performance Summary, then `[[SPLIT]]`, the closing "anderes Thema oder Q&A?" question ending with a `[[CHOICES kind=mode]]` button group (Tutor/Q&A) exactly like the welcome — three stacked bubbles. `ChatbotAnswer` renders the first segment in the main card and each extra segment as its own card, placing the option group on the LAST one; the extra cards are wrapped in a `.answerBubbleGroup` column (the `.chatMessageGpt` row is flex, so without it the bubbles tile side-by-side — single-bubble messages use `display:contents` so their layout is unchanged). The end-of-test re-offer is `kind=mode` (not `generic`); its Q&A button label is "I have a question"/"Ich habe eine Frage"/"Ik heb een vraag" (not "Ask a question"/"Fragen stellen", which the model misread as a tutor request). Keep the marker grammar (`[[CHOICES …]]` + `[[SPLIT]]`), the per-bot `options.*` i18n, the welcome marker, and the "🟠 P1 — INTERACTIVE OPTION MARKERS" prompt section in lockstep across all tutor bots; the HYROX assessment Start/Continue/Retry buttons likewise suppress their control-message user bubble (`isControlMessage`).
- The `hyrox-assessment` bot (HYROX Level 2 "Managing Performance" certificate) is NOT a tutor/RAG bot: it runs a backend-driven, stateless **module-by-module** knowledge assessment (no retrieval — `chatreadretrieveread._is_hyrox_assessment_chatbot` skips search). 52 questions in `app/backend/approaches/chatbots/hyrox_assessment/questions.py` (auto-generated; see Adding Data) are grouped into 13 modules (`M1`–`M6`, `M7.1`–`M7.4`, `M8`–`M10`), asked in fixed order; **all** questions of a module are asked, each module is scored separately at an **80% threshold**, a failed module is **retaken in full** until passed, and only after the **final** module passes is the run complete. State is reconstructed every turn (`results.py:derive_turn_state`) from hidden markers replayed in history: `[[PLAN]]` (run anchor), `[[MODULE m=.. attempt=..]]` (module-attempt anchor — its window scopes the current attempt's scores so a failed attempt never pollutes the retake), `[[ASKED q=K]]`, the model's `[[SCORE q=K points=".." max=Y mod="M.."]]` (per-key-point 0/1 verdict only; backend computes `awarded=min(sum,max_pts)`), `[[MODPASS m=..]]`/`[[MODFAIL m=..]]` (module-boundary signals that drive the frontend Continue/Retry buttons), `[[BREAK]]` (display bubble split), and — **only on the final module's pass** — `[[PROGRESS value=100]]` (→ `lemon://save_progress`, the LMS completion; never per-module) + `[[DONE]]` (terminal). The model writes NO numbers/headings/transitions/visible question text; the backend renders the module heading, per-module "Question N of M" counter, scores, module result, transitions, and the entire end sequence. The **end-of-assessment summary is model-authored, general, and spans all modules** (per the spec's "summary organized by topic … strengths and weaknesses … across all modules"): on the finalising turn of the FINAL question **only**, the model writes brief feedback, then `[[SUMMARY]]`, then a few general strengths + a few worth-revisiting take-aways (plain language, no numbers, no answer-dumping). `render_completion_bubbles` splits at `[[SUMMARY]]` — the take-aways become the summary bubble under the backend-supplied heading — and falls back to the **deterministic** `render_topic_summary` (one Strengths + one Worth-revisiting list of key-point topics aggregated across all modules via `module_topic_breakdown`, any topic missed *anywhere* → worth-revisiting so the two lists stay disjoint) when the model omits `[[SUMMARY]]`. The completion sequence also renders the **final module's own result line** (`render_module_result`, e.g. "**Module 10 complete — 25/25 (100%). Passed.**") as its own `[[BREAK]]` bubble BEFORE the cross-module "passed every module" result, so the final module is not the only one lacking an explicit per-module completion line like the non-final `render_module_end_bubbles` path shows (added 2026-07-23); it always reads as a pass since completion requires clearing it, and it reports the module's own point total (a strict subset of the grand total). Three independent safeguards keep the ending from leaking early or stalling the one-correction loop: (1) the prompt tells the model to emit `[[SUMMARY]]` ONLY when it actually finalises the final module's last question, and `build_state_injection` explicitly forbids any summary/take-aways on every other turn; (2) the below-full premature-finalisation guard in `render_assessment_turn` discards a below-full first-answer `[[SCORE]]` and cuts any ending, offering the correction instead; (3) `cut_premature_ending` runs on EVERY finalising turn that is not the true final-module completion (`is_completion_turn` = full marks on the final module's last question) — including a **full-marks or post-correction finalisation of a non-final question** — cutting a volunteered ending while preserving the `[[SCORE]]` so it still replays. Safeguard (3) closes the reported Module-10 leak (a full-marks answer on a non-final question dragged the whole summary into its per-question feedback because the below-full guard never ran on full marks). Detection (`ending_cut_index`) keys **only on the `[[SUMMARY]]` token** — the one signal that never appears in ordinary per-question feedback, so cutting has zero false positives; the prompt requires the model to precede ANY take-aways with `[[SUMMARY]]` and to write none except on the final turn. A prose/keyword matcher (Strengths/Worth-revisiting labels, completion phrases) was tried and **rejected**: adversarial review proved it cannot distinguish a real summary from legitimate feedback that merely reuses words like "worth revisiting"/"Strengths"/"complete", so it erased real learner feedback — a worse failure than the rare leak it prevented. A contract-violating **token-less** prose summary is therefore the documented residual (the prompt hardening covers it); it is benign (no false completion, `[[SCORE]]` still recorded). (A prior iteration made the summary a deterministic **per-module** breakdown with the model authoring nothing; that drifted from the spec — do not reintroduce per-module summary headings/bands.) `[[SUMMARY]]` is a **live** marker again; it is also kept in the Python `ANY_MARKER_RE`/`SUMMARY_TOKEN_RE` and the TS `ASSESSMENT_MARKER_RE` to display-hide the token itself and to cut stray take-aways. Per-question grading keeps the one-revision rule (the premature-partial-score guard). **Model-faked control markers are neutralised server-side** (2026-07-17, the "stuck after Module 10 passed" bug): production session logs showed the model imitating the boundary bubble — fabricated result line + the forbidden `[[MODPASS]]` — on ~8% of module boundaries, so `render_assessment_turn` now strips PLAN/MODULE/MODPASS/MODFAIL/PROGRESS/DONE/ASKED/BREAK from the model body (`strip_forbidden_model_markers`), stores `[[SCORE]]` in canonical backend form with the pinned `q` (`format_score_marker` — a verbatim-stored wrong `q` desynced the counter and re-asked the final question forever), and strips imitation module-result lines (`_MODULE_RESULT_LINE_RE`; `_COMPLETE_LINE_RE` also matches numbered "Module 10 complete" variants). `derive_turn_state` acts on the LAST boundary marker in the window (the backend's is always trailing — a fake MODPASS before the real MODFAIL once advanced a production learner past a failed module) and IGNORES a MODPASS for the final module (the backend never writes one there; treating it as a pass used to go terminal via `_completed_state()` WITHOUT the completion sequence or the LMS `[[PROGRESS]]` — legacy bricked sessions now self-heal on the learner's next message, see the boundary-recovery bullet below for why the fall-through alone was not enough). **The module boundary is rendered from state, not from a single event** (2026-07-29, the reported "Module 10 passed and the remaining bubbles never appeared" bug). The module result and the end-of-assessment sequence used to be emitted ONLY on the turn that finalises a module's last question, so any single-turn failure stranded the run forever: with a `[[SCORE]]` for every question of the attempt but no `[[MODPASS]]`/`[[MODFAIL]]`/`[[DONE]]` closing it, `derive_turn_state` returned `current_id is None` with `assessment_complete` False and `render_assessment_turn` rendered **nothing** — no completion bubbles, no `[[DONE]]` (so the input stayed live), no `[[PROGRESS]]` (no LMS completion, no certificate), no session-log write — on that turn and every turn after it, while the model (told only "Wait for the system") improvised "You're done". `derive_turn_state` now reports that as `module_attempt_complete`, and `_render_owed_module_boundary` renders exactly what the finalising turn should have: the module result + transition + `[[MODPASS]]`/`[[MODFAIL]]`, or — for a passed final module — the whole completion sequence with `[[DONE]]` + `[[PROGRESS]]`, cross-module totals, `just_completed=True`, and the LMS report. It is idempotent by construction (the marker it writes removes the condition), so the very next learner message converges no matter what went wrong; `record_assessment_session` must therefore NOT treat it as a no-op turn. The model's text is discarded there and `build_state_injection` tells it to write nothing — this state is reached precisely when a fabricated boundary bubble is what the learner is looking at. Two matching leaks were closed with it: every whole-line strip pattern now tolerates a leading list bullet / heading marker / blockquote arrow / emoji (`_LEAD` — one decorative character used to defeat all of them, which is how a fabricated "Module 10 complete — 25/25 (100%). Passed." reached a learner), and `_strip_backend_owned_prose` drops any line reproducing the backend's own fixed prose in ANY locale (pass lines, continue prompt, fail text, correction offer, no-answer/decline lines, motivational, closing, summary heading) — the screenshot's "Well done — you passed this module." is Module 1's `module_pass_lines[0]`, which the backend cannot render at Module 10, so it was provably the model's imitation. The strengths/worth-revisiting LABELS are deliberately NOT stripped (the model legitimately authors the take-aways body); because `sanitize_history_for_model` runs `strip_rendered_numbers`, this also removes the boundary bubble from the model's view of history, killing the imitation stimulus at source. Keep the boundary state-driven: never gate a terminal or one-shot render on a single turn's event. **A score must be earned: the backend owns the grading decisions, the model only judges key points** (2026-07-28, two reported failures — a learner who declined the correction was awarded FULL marks one turn after being told a key part was missing, and a learner who answered "no" was awarded FULL marks with the invented praise "you covered the whole-body postural demand well"). The model no longer decides anything about the flow: it emits its `[[SCORE]]` per-key-point verdict on EVERY grading turn (complete or not — it used to withhold the marker on a partial answer and write its own correction offer), and `render_assessment_turn` decides what that means. (1) **`[[PROV q=K points="…"]]`** is a new backend-authored marker: the PINNED verdict of the answer the single correction was offered on. It does not finalise the question (no `max`/`mod`; `_scores_in_window` ignores it, so the counter does not advance) — it exists so a judgement, once made, cannot drift. On a **decline** (`latest_answer_is_decline`) the backend finalises from the pin and **discards the model's fresh verdict** (logged when they differ); on a genuine **revision** it finalises at `merge_best_verdicts` (per-key-point union, so a point already earned can never be lost). Previously the first-attempt verdict was thrown away, so the decline turn re-graded the same unchanged text from scratch — that is bug 1 exactly. (2) **A refusal is not an answer**: `substantive_attempts_for_current == 0` forces `zero_verdict`, whatever the model claims (logged). The learner still gets one opportunity — the first refusal renders `answer_offer_no_attempt`, a second finalises at 0 with `no_answer_zero` — so a give-up no longer finalises on the spot (`must_finalize_current` now means "the correction was already offered", i.e. a `[[PROV]]` exists or an assistant turn followed the ask, or two learner messages arrived back-to-back). `is_give_up_or_meta` therefore covers bare refusals ("no", "nope", "nah", "nothing", "nein", "nee", …) — safe **only** because no pool question is yes/no-shaped (verified: 0 of 52 start with is/are/does/can/should), so re-check that if the pool ever changes. (3) **Feedback can't contradict the score**: on the two paths where the model has no new content to judge (forced zero, decline finalisation) the backend replaces the model's body with its own locale line and the injection tells the model to write nothing at all — that is bug 2's "wrong review". (4) **The rubric is pinned in the turn state**: `build_state_injection` now restates the pinned question's numbered key points in verdict order plus a strict "award 1 only if the learner's own words demonstrate it, never infer, never give the benefit of the doubt" rule, instead of leaving the model to locate the right rubric among all 52 questions in the pool — grading the wrong question's key points is a silent accuracy failure and the verdict array is positional. Keep `PROV` in the TS `ASSESSMENT_MARKER_RE` (display-hidden like every marker). One documented residual: if the model emits no `[[SCORE]]` on the offer turn (or an in-flight session predates `[[PROV]]`), a decline has no pin to finalise from and falls back to the model's fresh verdict — logged as `correction declined with no pinned verdict`. **A turn may never render an empty bubble** (2026-07-29, the reported blank answer to "idk"). The prompt tells the model to write *nothing at all* for a refusal because the backend authors those turns — so any refusal wording the backend does NOT recognise leaves neither side authoring the message, and the learner gets a blank bubble on that turn and on every retry (the question can never advance: nothing is scored, no `[[PROV]]` is pinned). Two layers: (1) `_GIVE_UP_CORE` must carry the wordings learners actually use — `idk`/`idc`/`dunno`/`no answer`/`beats me`/`have no idea` and the short de/nl forms were missing and `idk` alone caused the report; (2) `ensure_non_empty` guarantees visible text at every `render_assessment_turn` exit that can produce none (the terminal path, where the model likes to echo the stripped `closing_passed`, → `already_complete_note`; the main assembly path → `answer_not_assessed`), prepending the fallback so hidden markers still replay. The no-verdict branch deliberately does NOT replace the model's body when the model wrote something — it is also the legitimate path for declining an off-topic question and steering back, and that reply must reach the learner alongside the backend's offer/score. Adding a `_LOCALES` line the backend authors means adding its key to `_backend_owned_prose_keys()`. **A question is capped at two learner messages** (2026-07-29, requested after the same report). Message 1 either finalises at full marks or pins a verdict and offers the single revision; message 2 ALWAYS finalises; there is never a third. Every branch of the verdict resolution in `render_assessment_turn` must preserve that, and the branch flag is `is_final_message_for_question` = `state["must_finalize_current"]` — which is also true when two learner messages arrive back-to-back, so a double-send cannot buy an extra round (both messages are graded together). The cap is what forced the no-verdict branch to decide instead of stalling: it pins `provisional or zero_verdict` and offers on message 1, finalises from that pin on message 2. The zero pin never caps the learner — `merge_best_verdicts` unions it with whatever the revision earns, so a complete second answer still scores full marks. Backend copy on a message-2 turn where the model wrote nothing keys on the **awarded points**, not on which branch got there: >0 → `decline_keeps_answer` ("we'll go with your original answer"), 0 → `answer_not_scored` ("No points were awarded for this question.", deliberately claiming nothing about why, unlike `no_answer_zero`). The model is told the cap in both `sampleprompt.py` (PER-QUESTION PROTOCOL item 5 + a "Two messages per question" section) and every `build_state_injection` turn, and is told to react-and-zero rather than go silent on absurd/off-topic input — that instruction is what makes the *visible* reply fit what the learner actually typed; the backend paths above are the guarantee, not the copy. `tests/test_hyrox_assessment.py::test_the_two_message_cap_holds_for_any_input_and_any_model_behaviour` brute-forces learner input × model behaviour and must stay green. **No backend-rendered line may ever appear twice** (2026-07-28, the duplicated "**Question 2: 4/4**" bubble a customer saw). Same root cause as the faked markers, one level up: the backend renders its numbers INTO the stored assistant message, so every replayed turn showed the model score lines/headers over its own signature and it copied them (four production sessions printed the per-question score line twice — the backend's own line plus the model's identical imitation). Three layers now hold, and all three must stay: (1) `sanitize_history_for_model` strips the backend-owned lines and backend-only markers from the copy of the history sent to the LLM (`chatreadretrieveread.run_until_final_call`'s `past_messages`) — the model never sees a line it is forbidden to write, so the stimulus is gone; `derive_turn_state` and `record_assessment_session` keep the untouched history, and the model needs nothing from it because `build_state_injection` restates the module/counter/pinned question every turn; (2) `strip_rendered_numbers` covers **every** backend-rendered line shape — the "Question N of M" header, the per-question score line (`_QUESTION_SCORE_LINE_RE`, the one shape that had no rule until now — that gap *was* the bug), a bare score fraction (`_BARE_SCORE_LINE_RE`), the running total, the module result, the completion line, and the bare module heading (`_MODULE_HEADING_LINE_RE`) — each anchored to a WHOLE line so prose containing a number ("you covered 2/3 of the factors") is never touched, and re-applied after a `[[SCORE]]` marker is removed from the body so an imitation sharing that line becomes a whole-line match; (3) `drop_lines_duplicating` deletes from the model's text any line the backend is about to render in that same message (normalised: bold/spacing/punctuation-insensitive, marker-bearing lines never touched), wired into all four assembly paths (ask, mid-module chain, `render_module_end_bubbles`, `render_completion_bubbles` — where the target list includes the summary heading). Layer 2 catches wrong-number imitations; layer 3 catches shapes no regex anticipated. Adding a new backend-rendered line means adding it to layers 2 and/or 3. `tests/test_hyrox_live.py::assert_no_duplicated_rendered_lines` enforces the invariant against the real model. `app.py` sets the `hyrox_assessment` logger to APP_LOG_LEVEL so completion lines, marker-drift, and duplicate-line warnings surface in Container Apps logs. **Session logging:** every assessment turn upserts ONE blob per session at `content/hyrox-assessment-logs/<account_id>/<session_id>.json` via `record_assessment_session`, rewritten in place — so an **abandoned** run is on record with its full transcript. (Until 2026-07-28 a log was written only when the final module passed, which left every incomplete run with no server-side trace whatsoever: Cosmos chat history is off in the nerilio env, so an unfinished transcript existed only in the learner's own browser and was unrecoverable.) `status` (`in_progress`/`completed`) and `progress` distinguish them, `passed` is true only on completion, and `score`/`percent` are running accuracy over the questions finalised so far (progress through the assessment lives under `progress`, not in `percent`). `scores`/`module_breakdown` span every module finished so far because `run_scores_so_far` prepends `prior_module_results` — `render_assessment_turn` returns only the CURRENT module attempt's scores except on the completion turn, where it already flattens. `_start_module_state` therefore takes `prior_results` and MUST be given them: until 2026-07-29 it hardcoded `prior_module_results: []`, so the write on every module-start turn (Continue/Retry) described a run with **zero** questions finalised and overwrote the good record — the interleaved "0/52 questions finalised" writes in the production logs, which left a run abandoned right after tapping Continue on record as having done nothing. A terminal/no-op turn (post-completion chatter, nothing to grade) writes NOTHING: `render_assessment_turn` returns empty scores there, so a write would replace a finished record with an empty one — but a `module_attempt_complete` boundary-recovery turn is NOT one of those (it carries the attempt's real scores) and must not be skipped. The LMS report stub still fires exactly once, on completion. Sessions launched outside the Lemon LMS carry no `account_id` and bucket under `anonymous/`. Two accepted residuals: these blobs sit in the `content` container, which `/content/<path>` serves unauthenticated (`AZURE_USE_AUTHENTICATION=false` → `check_path_auth` returns True), so a learner's name plus full transcript is fetchable by anyone holding the exact blob name; and the storage account has no lifecycle policy, so logs accumulate indefinitely. Known residuals (accepted): a token-less model ending on the final question's correction-offer turn still displays (documented above) and recovers on the next message; `run_with_streaming` performs no assessment rendering (unreachable — the bot hard-forces non-streaming). The Python marker set in `results.py`/`sampleprompt.py` and the TS set in `components/Answer/assessmentMarkers.ts` (+ `pages/chat/Chat.tsx` boundary buttons) must stay in lockstep; `questions.py` has `len(key_points) == max_pts` for every question (one point per key point). - The snap.de **and nerilio.ai** websites (both in category `snap`, one merged `data/snap.json` feed that keeps the `"feed": "snap.de"` marker) have a full end-to-end refresh script: `app/backend/refresh_snap.py`. Run it with the backend venv while azd-logged-in; it (1) change-checks a per-site watermark in `data/snap.state.json` (`--force` to bypass, `--check-only` to just report) — snap.de via WP-REST latest-modified/counts plus a hash of the rendered homepage header/footer markdown, nerilio.ai via sitemap + per-page HEAD `Last-Modified`/`ETag`; a change on **either** site triggers the full refresh — then (2) re-scrapes `data/snap.json` (markdown via `scripts/scrape_snap.py`), then (3) deletes category `snap` and re-indexes through the custom snap parser (`delete_category_data.py` + `prepdocs.py`). snap.de body content comes from the WP REST API; because that API returns no theme chrome, the header/footer (offices, phone/fax, e-mail, nav, legal links) is scraped from the rendered homepage into a dedicated `website-header-footer` site-info document. nerilio.ai is a pre-rendered static React site (no WordPress): pages are crawled from `sitemap.xml` (+ same-site link discovery), per-page content excludes the repeated header/footer/nav chrome (captured once as `nerilio-website-header-footer`), FAQ answers are pulled from the pages' schema.org FAQPage JSON-LD (the visible accordion DOM carries only questions), and all nerilio record ids are prefixed `nerilio-` so they cannot collide with snap.de ids. The scrape fails hard (and `refresh_snap.py` additionally validates) unless BOTH sites contributed documents, so a partial outage can never half-wipe the index; it scrapes before deleting and writes the watermark only on success, so a failed run is safely retried. Automation (webhook/schedule) is intentionally deferred — it is a manual command for now.
- The **breitband.tirol** website (category `bbsa`, feed `data/bbsa.json` marked `"feed": "breitband.tirol"`) has the same shape of end-to-end refresh script: `app/backend/refresh_bbsa.py` (change check → `scripts/scrape_bbsa.py` → `delete_category_data.py` + `prepdocs.py`), with the watermark in `data/bbsa.state.json` and the same `--force`/`--check-only` flags and scrape-before-delete safety. It is WordPress + **Elementor**, and content comes from the WP REST API (`pages`, `posts`, and the `gemeinde` custom post type). **One WordPress install is served on a wildcard subdomain per municipality** (`schwoich.breitband.tirol`, …) and the REST API is host-aware: the *same* page IDs return municipality-specific rendered content per host. Only `gemeindeinfos` (build status, who pays for the house connection, the local contact person, the providers active on that municipality's network) and the `home` hero line actually vary — everything else is byte-identical across hosts. So the shared pages are scraped **once** from the main host and each municipality contributes **exactly one** document (`gemeinde-<slug>`, titled with the municipality name, `url` = its own `…/gemeindeinfos/`), assembled from one REST list request per subdomain. Indexing every page for every host was deliberately rejected: ~90% would be duplicate boilerplate, which degrades retrieval and points citations at arbitrary subdomains. `breitband.tirol/gemeinde/<slug>/` is only a directory stub (renders chrome and nothing else), so the `gemeinde` post type is used purely as the municipality list **and** as the per-municipality change watermark — its records carry their own `modified` timestamps, which is the only thing that moves when a municipality's Elementor fields are edited (the shared page IDs never do), so `pages`/`posts` watermarks alone would miss every municipality edit. `MIN_CONTENT_CHARS`/`SKIP_PAGE_SLUGS`/`GEMEINDE_CONTENT_SLUGS` in the scraper encode which pages are shells, superseded copies (`home-alt`, `notpublished`), or per-municipality; the statewide portal and the municipality website template are BOTH live and share page titles ("FAQs", "Deshalb Glasfaser", …) with different copy, so the template ones get a `(Gemeinde-Website)` title suffix to keep them apart in a citation list. Both halves of the feed must be non-empty or the scrape and `refresh_bbsa.py` abort before the delete. The HTML→markdown converter is imported from `scrape_snap` (one converter, two sites); the HTTP layer is owned by `scrape_bbsa` so requests carry a bbsa User-Agent. Automation is likewise deferred — manual command for now.
- Moodle and PublishOne XML feeds are auto-indexed from `content/nerilio/Nerilio-Moodle/` and `content/nerilio/Nerilio-Amsterdam/` (the PublishOne feed's source drop folder; renamed from `Nerilio-PublishOne`, category/target still `publishone`), mirrored into `content/moodle/` or `content/publishone/`, and indexed into Azure AI Search with categories `moodle` and `publishone`.
- FHG JSON feeds are auto-indexed from `content/nerilio/Nerilio-fhg/`, mirrored into `content/fhg/`, and indexed into Azure AI Search with category `fhg` using the FHG JSON parser.
- Provisioned ("generic") bot knowledge-base files are dropped by the nerilio side into the dedicated `content2` container as `content2/<bot_name>/<file>` and are auto-indexed into `category=<bot_name>` by the `content2` dynamic indexer using **generic parsers only** (`.pdf/.html/.txt/.md/.csv/.json/.xml`; no Document Intelligence, so Office/images are skipped). Files are indexed **in place — NOT mirrored** into `content`. Deleting a `content2/<bot_name>/<file>` blob removes its indexed docs (category + exact source storageUrl). See the content2 contract bullet under "Contracts To Preserve".
- The feed parser maps outer `<document id="...">` to `sourcepage`, direct `<naam>` to `title`, `url` to the external PublishOne document URL, structured document text into `content`, and extra metadata into `tags`; citations use first-class `title` and `url`.
- The six content-specific custom parsers all dispatch from `parse_file` (`app/backend/prepdocslib/filestrategy.py`), so they fire on BOTH the ingestion scripts AND manual `/admin/uploads` when the file lands in the matching category: HYROX JSON (`hyroxjson.py`, category `lemon`, content-sniffed), lemon knowledge XML (`lemonxml.py`, category `lemon`, `<knowledge>`-root-sniffed, one doc per `<chunk>`), snap/nerilio JSON (`snapjson.py`, category `snap`, `feed` marker), breitband.tirol JSON (`bbsajson.py`, category `bbsa`, `"feed": "breitband.tirol"` marker), FHG JSON (`fhgjson.py`, category `fhg`, dict-with-`documents`), and Moodle/PublishOne XML (`publishonefeed.py`, categories `moodle`/`publishone`). Category `lemon` has two parsers (HYROX JSON, lemon XML) that stay disjoint via the extension gate. `snapjson.py` and `bbsajson.py` are sibling web-scrape feeds with the same record shape; they stay disjoint via category **and** feed marker, so a mis-categorized upload falls through to the generic parser instead of being silently mis-parsed. A non-matching category falls back to the generic extension parser. Section ids are deterministic, so a managed upload and the Azure Function feed overwrite the same search docs; keep the `if_applicable` dispatchers in sync with the standalone builders (and re-run `scripts/copy_prepdocslib.py`). No bot under `approaches/chatbots/` has its own parser (e.g. bensberg uploads PDFs → generic PDF parser).
- Deleting one of those source XML blobs must remove the mirrored target blob and matching indexed documents.
- To purge one category from both Azure AI Search and blob storage without re-ingesting, run
  `python app/backend/delete_category_data.py <category>`; it deletes search docs with
  `category=<category>` and blobs under `content/<category>/`. To purge only the search index, run
  `python app/backend/delete_documents_by_category.py <category>`.

## Adding A Chatbot

Frontend:

1. Create `app/frontend/src/chatbots/<chatbot_name>/`.
2. Export `name`, `LayoutWrapper`, `Chat`, `NoPage`, and `i18n` from `app/frontend/src/chatbots/<chatbot_name>/index.ts`.
3. Register it in `app/frontend/src/chatbots/registry.ts`. The entry must also supply `ChatbotMetadata` shown on the chatbot directory cards: `llm`, optional `reasoningEffort` (only when the model is in the backend `GPT_REASONING_MODELS` map), `mode` (`"qna"` for Q&A-only prompts, `"tutor-qna"` for dual-mode prompts), and `agenticRetrievalDefault` (`true` only when the chatbot's `Chat.tsx` auto-checks the agentic-retrieval toggle, e.g. `lemon`'s `setUseAgenticRetrieval(config.showAgenticRetrievalOption)`). For chatbots whose `config.py` leaves `chatgpt_model`/`reasoning_effort` unset, mirror the values from the deployment `.env` (currently `.azure/agentic-retrieval-nerilio/.env` is the active one).
4. Add its theme in `app/frontend/src/chatbots/shared/theme/chatbotThemes.ts`; prefer a single `primary` color unless overrides are needed.
5. Add chatbot-specific i18n setup and `en`, `de`, `nl` translation files.
6. Prefer re-exporting shared `Example` and building answers with `app/frontend/src/chatbots/shared/answer/createBotAnswer.tsx`.
7. If chatbot auth is needed, gate it in that chatbot's `layoutWrapper.tsx` and standalone `NoPage` route.

Backend, always required for routing:

- Add the chatbot name to `KNOWN_CHATBOT_NAMES` in `app/backend/app.py`. The `/<chatbot_name>` route gates against this set and redirects unknown names to `/`, so a bot missing here loads as a redirect to the home page even though the frontend route exists.

Backend, only when custom behavior is needed:

1. Add `sampleprompt.py` under `app/backend/approaches/chatbots/<chatbot_name>/` for default prompt variables.
2. Add `contentfilter.py` only if the default localized copy is insufficient.
3. Add `config.py` for different model, deployment, reasoning effort, prompt-time values, prompt mode, or citation target.

`internal` is the exception: it has a frontend shell but no active backend `sampleprompt.py` or upload manager at runtime. Internal behavior routes through the selected `source_chatbot`.

## Adding An azd Variable

When adding an azd environment variable, update:

1. `infra/main.parameters.json`

Frontend:

## Tests And Checks

- Use pytest for backend and integration tests. Activate the virtual environment first.
- UI changes need Playwright e2e coverage where behavior matters. Build the frontend before e2e tests with `npm run build` in `app/frontend`.
- API endpoints need app integration tests, usually in `tests/test_app.py`.
- Functions and methods need focused unit tests.
- Use mocks from `tests/conftest.py`; prefer HTTP/request-level mocking when practical.
- Changing chatbot backend config loading requires tests for `app/backend/approaches/chatbot_config_registry.py` plus startup behavior for per-bot `ChatReadRetrieveReadApproach` overrides.
- Changing shared chatbot UI wrappers such as `createBotAnswer.tsx` or shared `Example` needs e2e coverage for bot-specific behavior that still matters, such as `rak` user-scoped citations or wordmark answer branding for `sartorius` and `steuertipps`.
- For coverage, run `pytest --cov --cov-report=annotate:cov_annotate`; inspect generated files and add tests for lines marked with `!`.
- Type-check application code and scripts with `ty check`.
- Backend dependency upgrades use `cd app/backend && uv pip compile requirements.in -o requirements.txt --python-version 3.10 --upgrade-package <package-name>`.

## Deployment

- `azd up` provisions Azure resources and deploys application code.
- Windows deployments also need Azure CLI (`az`) on `PATH` because `scripts/setup_moodle_delete_event_subscription.py` configures Event Grid subscriptions after deploy.
- Use `azd provision` for Bicep-only changes.
- Use `azd deploy` for app-code-only changes.
- For individual cloud ingestion functions, use commands such as `azd deploy document-extractor`, `azd deploy figure-processor`, or `azd deploy text-processor`.
- Azure Container Apps custom-domain portal bindings can be overwritten by provisioning. Preserve existing binding with `SERVICE_BACKEND_RESOURCE_EXISTS`, or manage it with `AZURE_CONTAINER_APP_CUSTOM_DOMAIN` and `AZURE_CONTAINER_APP_CUSTOM_DOMAIN_CERTIFICATE_ID`.
- `AZURE_SPEECH_DISABLE_LOCAL_AUTH=false` keeps Speech "Allow API key based authentication" enabled across `azd up`; set it to `true` only for intentional Microsoft Entra ID-only access.
